# 并发编辑、上传重试、权限变化与五大验收场景

## 乐观并发：两人调整同一镜头

每次时间线保存都要求客户端带 `base_version`：

* 后保存者的 base 落后于库中最新版本 → HTTP 409 `VERSION_CONFLICT`，
  并返回 `current_version`；**绝不**后写覆盖先写。
* 前端不强行自动合并（避免把同事的规则卡片静默丢掉），而是提示刷新后合并再保存。
* 用例：`test_two_editors_same_clip_conflict`（bob 先存 v2，evelyn 基于 v1 存 → 409；
  evelyn 刷新到 v2 后存 → v3）。

## 上传重试与断点续传

`upload_sessions` 记录 `chunk_size / received / sha256 / status`：

* 前端按固定 64KB+ 切片 PUT 到 `/api/uploads/{id}/chunks/{i}`，按字节偏移写入同一临时文件；
* **同一分片重发幂等**（网络超时后重传不会损坏文件）；
* 完成时服务端整体 sha256 + 长度校验，不一致返回 `SIZE_MISMATCH` 让前端继续补片；
* `GET /api/uploads/{id}` 返回已收字节，刷新页面后可从断点继续；
* 登记素材必须引用已完成上传的 sha256（内容寻址入库，相同字节重复上传只保留一份）。
* 用例：`test_chunked_upload_retry_and_complete`（重发分片 0、完成接口重复调用均成功且
  sha256 与本地一致）。

## 权限变化时恢复上次项目

* 成员角色分 owner/editor/viewer；编辑/发布要求 editor+，成员管理仅 owner。
* `/api/projects/{id}/resume` **当场**查成员资格：已被移除 → 403 `MEMBERSHIP_REQUIRED`
  （不返回空项目、不退回只读副本）；仍有资格才返回最新可编辑版本并更新游标。
* 用例：`test_resume_after_permission_revoked_is_403` 与
  `test_role_forbidden_for_viewer`。

## 场景一：入住规则修订

新规则只增版本；卡片钉的是旧 `rule_version_id`。发布日（`as_of`）：卡片版本不生效或
已有更新生效版本时分别报 `RULE_NOT_EFFECTIVE / RULE_REVISION_STALE`，重挂新版本后才能
发布。已发布导出的快照里保留的仍是旧规则原文。用例：`test_rule_revision_blocks_stale_card`。

## 场景二：照片来源失效

`asset_versions.source_status` 记录外部图床探测结果（ok/unreachable）。发布门遇到
unreachable 报 `PHOTO_SOURCE_UNREACHABLE` 阻断；引用/复制语义不变——副本 blob 在本地
内容寻址存储里，外部链接失效不影响已复制镜头的历史复现，但引用外部来源的新发布会被拦。
用例：`test_dead_photo_source_blocks_publish`。

## 场景三：两人调整同一镜头

见上"乐观并发"。补充：项目版本是整文档版本（不是单镜头锁），因为镜头之间存在顺序、
渠道坐标与转场关联；冲突粒度选在文档级以避免跨镜头不一致。

## 场景四：上传重试与恢复

见上"上传重试"。Web 上传按钮模拟一次随机分片失败，再点一次即从断点续传；
服务端不依赖前端状态，仅凭偏移与最终哈希保证正确性。

## 场景五：恢复上次项目时权限改变

见上"权限变化"。配合首页游标：即使权限后来恢复，游标仍指向用户离开时的项目版本，
不会把别人的新编辑误当成"我的上次进度"。

## 工作器排队期间状态变化

即使通过了点发布那一刻的检查，工作器 claim 任务后仍重新执行完整 dependency report：
授权撤回（`LICENSE_WITHDRAWN`）、来源失效等在排队窗口发生，任务标记 failed 且不产出
导出。用例：`test_worker_recheck_blocks_job_after_revocation`。
